빌드가 빨라졌다고 바로 운영에 올릴 수 있는 것은 아니었습니다.

빌드 성공은 "번들이 만들어졌다"는 뜻입니다. 운영 가능한 상태라는 뜻은 아닙니다. 특히 오래된 UI 프로젝트에서는 이 차이가 큽니다. 빌드 도구가 바뀌면 번들 파일명, 청크 분할 방식, 폴리필 로딩 순서, 런타임 전역 객체 처리, 데코레이터 변환 결과가 함께 바뀝니다. 브라우저에서 사용자가 실제로 조작하는 화면이 기존과 같다는 보장은 없습니다.

그래서 마지막으로 다룬 문제는 속도가 아니었습니다.

어떻게 검증하고 유지할건지, 기존 레거시 코드를 어떻게 동기화 할지, 롤백 시나리오 등 운영 반영 가능한 상태로 만드는거였습니다.

## 레거시 UI와 터보 UI를 나란히 올리기

레거시와 터보의 어떻게 동등성을 검증할 수 있을까?

로컬 확인과 개발기 검증은 성격이 달랐습니다. 로컬에서는 빌드가 되는지, 화면이 뜨는지, 주요 라우터가 깨지지 않는지를 빠르게 확인할 수 있습니다. 하지만 실제 개발기 서버에 올라가야만 드러나는 문제가 따로 있었습니다.

- 로컬 빌드는 보통 개발용 설정으로 실행되기 때문에 minification이 빠져 있습니다. 운영 또는 개발기 배포 빌드에서만 실행되는 압축 단계에서 문법 처리, 전역 객체 참조, dead code 제거 같은 문제가 드러날 수 있습니다.
- 로컬은 이전 빌드 캐시가 남아 있는 웜 빌드가 많습니다. 반면 Jenkins 개발기 빌드는 워크스페이스를 비운 상태에서 시작하는 콜드 빌드에 가깝습니다. 이 차이 때문에 로컬에서는 통과한 의존성 설치, 파일 해석, 캐시 무효화 문제가 개발기에서만 실패할 수 있습니다.
- 로컬에서는 파일이 같은 디렉터리에서 바로 서빙되지만, 개발기에서는 빌드 산출물이 실제 배포 경로로 복사되고 서버가 그 파일을 서빙합니다. 이때 `[contenthash]`가 붙은 청크 파일, lazy chunk, CSS, 이미지 같은 정적 리소스가 빠짐없이 올라갔는지 확인해야 합니다. 특히 동적 `import()`로 쪼개진 파일이 하나라도 누락되면 초기 화면은 떠도 특정 화면 진입 시 chunk 404가 발생할 수 있습니다.

그래서 기존 개발기 환경을 내리고 터보 UI를 올리는 방식보단 레거시 UI와 터보 UI를 나란히 배포하는 방법으로 진행했습니다.

![image.png](/assets/img/frontend/2026-05-24-frontend-01.png)

QA팀에서 두 화면을 브라우저 탭에 나란히 열고 같은 동작을 반복할 수 있습니다. 터보 UI에서만 이슈가 발견되면 JIra를 생성하여 파악합니다. 기존 UI에서도 동일하게 실패하면 기존 버그나 데이터 문제로 분류할 수 있습니다.

복구도 쉬워집니다

순차 교체 방식에서는 터보 빌드 UI에 문제가 생겼을 때 레거시 UI를 다시 빌드하고 배포해야 합니다. 레거시 빌드가 오래 걸리는 상황에서는 이것만으로도 큰 부담입니다. 병렬 배포에서는 신규 환경을 검수 대상으로만 두고, 문제가 생기면 기존 환경을 그대로 기준선으로 유지할 수 있습니다.

검증의 핵심은 "새 빌드가 뜨는가"가 아니었습니다.

"레거시 UI와 같은 조건에서 같은 방식으로 동작하는가"였습니다.

## QA 검수 방식

이 프로젝트에는 이미 갖춰진 E2E 테스트 인프라가 없었습니다. React 버전도 오래됐고, 서비스 수가 많았으며, 복잡한 실제 업무 데이터 흐름이 얽혀 있었습니다. 이 상태에서 Playwright나 Cypress 같은 도구를 새로 도입해 전수 자동화를 만드는 것은 별도 프로젝트에 가까웠습니다.

그래서 수동 QA와 런타임 모니터링을 조합했습니다. 수동 QA는 정해진 시나리오로 스모크 테스트를 진행하고, QA가 확인하지못한 스크립트에러를 확인하는 방식으로 진행하였습니다.

QA팀에서는 레거시 UI와 터보 UI를 두 탭에 나란히 열어, 같은 계정으로 로그인합니다. 같은 서비스에 진입합니다. 같은 데이터를 클릭하고, 같은 검색어를 넣고, 같은 저장 동작을 실행합니다. 콘솔과 네트워크 탭도 함께 확인합니다.
운영기에 나갔을때도 동일하게 검수할 수 있도록 서비스별 체크시나리오를 정해놓고 진행했습니다.

```
- 기존 UI 정상, 신규 빌드 UI 실패: 롤백 or 이슈분석
```

이 방식은 수치로 표현되지 않습니다. 하지만 당시 조건에서는 가장 현실적인 방법이었습니다. 자동화 테스트를 도입하지 않았다는 사실을 감추기보다, QA팀이 할수 있는 영역과 모니터링이 보완하는 영역을 나누는 편이 더 안전했습니다.

## 모니터링 수치로 판단하기

QA팀은 정해진 시나리오를 확인합니다. 하지만 사용자는 정해진 시나리오대로만 움직이지 않습니다.

특정 데이터 상태에서만 깨지는 화면이 있습니다. 특정 브라우저에서만 발생하는 오류가 있습니다. 오래 머물렀을 때만 발생하는 비동기 오류도 있습니다. 레거시 UI에서는 이런 문제가 늦게 발견되기 쉽습니다.

그래서 신규 빌드 UI에는 빌드 단계부터 런타임까지 세 영역에 모니터링을 붙였습니다. 빌드 시간 추이, 에러 발생, 성능 지표를 각각 수집했습니다.

### 빌드 모니터링

빌드 단계에서는 다음 값을 모니터링 시스템으로 보냈습니다.

| **필드** | **의미** |
| --- | --- |
| `buildSec` | 순수 빌드 시간 |
| `installSec` | 의존성 설치 시간 |
| `buildVariant` | 기존 UI / 신규 빌드 UI 구분 |
| `commit` | 빌드 대상 커밋 |
| `branch` | 빌드 브랜치 |
| `jobName` | CI Job 이름 |

빠른 빌드를 만들었다면 그다음은 빠른 빌드가 계속 빠른지 확인해야 합니다. 빌드 시간 추이를 대시보드에 함께 넣었습니다. 특정 커밋 이후 콜드 빌드가 100초를 넘기 시작한다면, 대형 파일이 추가됐는지, sourcemap 설정이 다시 켜졌는지, 캐시 설정이 잘못 들어갔는지 추적할 수 있습니다.

이제 빌드 시간은 Jenkins 로그로 확인하는게 아니라, 모니터링 화면에서 계속 보이는 지표가 됐습니다.

![image2.png](/assets/img/frontend/2026-05-24-frontend-04.png)

### 에러 수집

JS 런타임 오류(`script_error`)와 Promise 미처리 거부(`unhandled_rejection`) 두 종류로 나뉘며, 각 이벤트에 `buildVariant` 필드를 함께 기록해 turbo와 legacy를 구분할 수 있게 했습니다.

| **지표** | **보는 이유** |
| --- | --- |
| `script_error` 건수 | JS 런타임 에러 전체. 전역 객체 누락(`ReferenceError`)도 여기서 잡힘 |
| `unhandled_rejection` 건수 | `window.onerror`가 못 잡는 Promise 에러 전용. lazy chunk 로드 실패(`ChunkLoadError`)와 Babel 6 → SWC 전환 시 async/await 폴리필 회귀가 모두 여기서 나옴 |
| RISK A 등급 에러 건수 | 결제·가입 등 핵심 URL에서 발생한 에러만 별도 집계 |

레거시 UI는 Babel 6의 `.babelrc`에서 `stage-1` 프리셋을 사용하고 있었습니다. `stage-1`은 실험적 문법을 관대하게 허용해, 표준에서 벗어난 표현이 빌드 단계에서 조용히 통과되는 경우가 있었습니다. SWC로 전환한 뒤에는 `loose: false`가 기본이 되면서, 이전에는 넘어가던 문법 이슈가 런타임 오류로 드러나기 시작했습니다. 에러 수집의 초기 단계는 이 오류들을 수집하고 하나씩 수정하는 과정이기도 했습니다.

### 성능 지표

이번 프로젝트의 목표는 빌드 시간 단축이었습니다. 성능 지표는 신규 빌드 UI가 기존 UI 대비 크게 나빠지지 않았는지 이상치를 확인하는 참고용으로만 수집했습니다. 레거시 서비스 특성상 두 빌드 모두 절대 수치가 빠르지 않아, 수치 자체의 개선은 이번 범위 밖이었습니다.

| **지표** | **보는 이유** |
| --- | --- |
| LCP | 메인 콘텐츠(가장 큰 요소)가 완전히 그려지는 시점 |
| FCP | 첫 텍스트/이미지가 화면에 그려지는 시점 |
| CLS | 로딩 중 레이아웃이 튀는 정도 |
| TTFB | 서버 응답 문제가 프론트엔드 문제처럼 보이는지 분리 |

## 기존 레거시 동기화

신규 빌드 UI는 별도 레포에서 시작했습니다.

운영 중인 레거시 레포에서 바로 Webpack 5와 SWC 전환을 진행하면 다른 개발자에게 영향을 줄 수 있기 때문에 레포를 분리하여 진행했습니다.

하지만 분리된 레포에는 새로운 문제가 있습니다.

기존 레거시 레포의 기능 개발은 계속 진행됩니다. 그동안 신규 빌드 레포가 멈춰 있으면 두 레포는 금방 벌어집니다. 운영 이관 직전에 한꺼번에 합치려 하면 충돌 위험과 동기화 작업 비용이 커집니다.

그래서 동기화 파이프라인을 만들었습니다.

![image4.png](/assets/img/frontend/2026-05-24-frontend-07.png)

동기화는 단방향으로만 진행됩니다. 기존 레거시 레포에서 신규 빌드 레포로만 갑니다. 그리고 기존 레거시 CI가 성공한 뒤에만 실행했습니다. 깨진 코드가 신규 빌드 레포로 바로 전파되는 일을 막기 위해서였습니다.

동기화 대상도 제한했습니다.

| **대상** | **동기화 여부** | **이유** |
| --- | --- | --- |
| 비즈니스 소스 | 포함 | 실제 기능 변경 |
| 정적 리소스 | 포함 | 랜딩 파일 |
| Webpack 설정 | 제외 | 신규 빌드 레포 전용 설정 |
| 패키지 설정 | 제외 | 내부 패키지 고정 방식이 다름 |
| SWC 설정 | 제외 | 신규 빌드 레포 전용 컴파일러 설정 |
| 빌드 스크립트 | 제외 | 레포별 운영 방식이 다름 |

### 커밋 체크포인트로 동기화 위치 추적하기

처음에는 단순히 특정 디렉토리를 checkout하는 방식도 생각했습니다. 하지만 이 방식은 커밋 히스토리를 잃습니다. 누가 어떤 변경을 했는지, 원본 커밋이 무엇인지 추적하기 어렵습니다.

최종적으로는 커밋 단위로 반영하는 방식을 택했습니다.

핵심은 `.legacy-sync-point` 파일입니다. 이 파일 한 줄에 "마지막으로 신규 빌드 레포에 반영된 레거시 커밋 SHA"가 기록됩니다. 동기화 스크립트는 이 SHA 이후의 레거시 신규 커밋만 골라 순차적으로 적용합니다. 동기화가 끝나면 파일을 최신 SHA로 갱신하고 `chore: update legacy sync point` 커밋으로 남깁니다.

```
# .legacy-sync-point 예시
1007a9d9f1777e4fc376ce8b4c5273ec7801ff00
```

그리고 신규 빌드 레포에 생성되는 각 동기화 커밋에는 `Legacy-Commit:` 메시지를 추가했습니다.

```
[HELP-405XXX] 특정 서비스 목록 정렬 기준 수정

Legacy-Commit: 3a8f21c...
Legacy-Repo: legacy-ui
```

작성자, 작성 날짜, 커밋 메시지가 그대로 보존되고 원본 레거시 SHA가 메시지로 기록됩니다. 장애가 생겼을 때 "어떤 기존 레거시 커밋이 신규 빌드 UI에 들어온 뒤 문제가 생겼는가"를 `git log --grep="Legacy-Commit:"` 한 줄로 추적할 수 있습니다.

### 동기화 전에 먼저 해결해야 했던 것

신규 빌드 레포의 소스는 기존 레거시 소스를 그대로 둔 상태가 아니었습니다. SWC 전환 과정에서 기존 Babel 6가 통과시키던 문법 중 일부를 직접 수정했습니다. `System.import()`는 표준 동적 `import()`로 바꿨습니다. 일부 JSX 문법 오류와 `.js` 파일 안의 TypeScript 타입 표기도 정리했습니다. 중복 폴리필 import도 제거했습니다.

이 수정이 기존 레거시 레포에 반영되지 않은 채 동기화를 돌리면, 신규 빌드 레포의 호환성 수정이 다시 덮어써질 수 있습니다. 다행히 이 수정들은 Babel 6와 SWC 양쪽에서 모두 동작하는 표준 문법 범위 안에 있었습니다. 레거시 빌드를 깨뜨리지 않고 동일하게 반영할 수 있었고, 이후 동기화에서도 이 수정이 유지될 수 있었습니다.

동기화 파이프라인에는 내부 패키지 drift 검사도 넣었습니다.

내부 Git 패키지를 tgz로 고정한 뒤에는 또 다른 문제가 있습니다. 원본 내부 패키지가 바뀌었는데 신규 빌드 레포의 tgz 고정본이 그대로이면, 두 환경의 컴포넌트 버전이 달라집니다. 그리드나 캘린더 같은 공통 패키지는 화면 회귀로 이어질 수 있습니다.

![스크린샷 2026-05-22 오후 5.46.07.png](/assets/img/frontend/2026-05-24-frontend-08.png)

그래서 내부 패키지 고정본의 원본 커밋과 체크섬을 manifest로 남겼습니다. Jenkins 빌드 전에 현재 원본과 manifest를 비교하고, drift가 있으면 빌드를 막았습니다.

동기화의 목적은 코드를 자동으로 복사하는 것이 아니었습니다.

분리된 신규 빌드 레포가 운영 이관 전까지 기존 레거시 개발 흐름을 놓치지 않게 하는 것. 그리고 문제가 들어왔을 때 어느 커밋에서 들어왔는지 추적할 수 있게 하는 것이었습니다.

## 롤백 시나리오

마지막으로 롤백 시나리오를 세웠습니다.

롤백은 장애가 난 뒤에 생각하면 늦습니다. 특히 프론트엔드 번들은 정적 파일처럼 보이지만, 실제로는 API, 인증, 브라우저 캐시, chunk 로딩과 연결되어 있습니다. 배포 직후 화이트스크린이 뜨거나 chunk 파일이 404를 내면, 원인을 분석하는 동안 사용자는 계속 막혀 있습니다.

핵심 전제는 하나였습니다. 롤백은 "다시 빌드하는 것"이 아니어야 한다는 것입니다.

### 병렬 빌드 기반 롤백 구조

레거시 JOB과 터보 JOB은 항상 같은 소스를 기준으로 나란히 빌드됩니다. 동기화 파이프라인이 레거시 레포의 최신 변경을 터보 레포로 반영하고, Jenkins는 두 JOB을 동시에 실행합니다. 두 JOB이 모두 성공하면 각각의 번들 파일이 Jenkins 서버에 저장됩니다.

배포는 터보 빌드 산출물을 기준으로 진행합니다. 하지만 레거시 빌드 산출물도 Jenkins 서버에 그대로 남아 있습니다. 재빌드 없이 언제든 꺼낼 수 있는 상태입니다.

QA팀은 배포 직후 서비스별 체크 시나리오에 따라 스모크 테스트를 진행하고, 스크립트 모니터링 지표를 함께 확인합니다. 이상이 없으면 배포를 확정합니다. 동작 오류나 이슈가 발견되면 이미 Jenkins 서버에 저장된 레거시 빌드 산출물을 바로 꺼내 배포합니다.

레거시를 다시 빌드하는 시간이 없습니다. 산출물이 이미 준비되어 있기 때문에 롤백은 배포 경로만 바꾸는 일입니다.

![image5.png](/assets/img/frontend/2026-05-24-frontend-09.png)

롤백 후에는 로그인, 공통 내비게이션, 변경 빈도가 높은 화면, 내부 패키지 영향을 받는 화면을 우선 확인합니다. 운영이 안정화된 뒤에는 포스트모텀을 작성합니다. 언제 감지했고, 어떤 이슈였고, 정상화까지 얼마나 걸렸고, 재발 방지 조치는 무엇인지 남깁니다.
